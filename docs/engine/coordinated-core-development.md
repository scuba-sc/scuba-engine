# Coordinated Core development profile

This is the current development integration path, not a release or game-runtime acceptance. It consumes an unpublished `2.4.1-dev.1` host-source SDK built from clean coordinated Core commit `d06f9124d6d7d380295ada4bc2af8968b98a051c`. Its filename is `sco-sdk-host-source-sc-2.4.1-dev.1.zip`. The version names development bytes and does not imply a GitHub release tag. The audited host-source archive has SHA-256 `d8118e8898de8daac0cff6f4c9b645cd722a32a5b5924c21c7dae2538074323a`. Do not use the outer bundle digest, the published `2.4.0` digest, or the historical bf56 rehearsal digest for this archive.

With a full toolchain, package the final clean, exact Core checkout using its development mode, preserving Git executable modes on all platforms:

```sh
set -eu
git -C /path/to/coordinated-core status --porcelain
test "$(git -C /path/to/coordinated-core rev-parse HEAD)" = d06f9124d6d7d380295ada4bc2af8968b98a051c
test -z "$(git -C /path/to/coordinated-core status --porcelain --untracked-files=all)"
python tools/package_dev_sdk.py /path/to/coordinated-core /path/to/assets --development
python /path/to/coordinated-core/tools/ip_audit.py zip --development --profile host-source-sc \
  /path/to/assets/sco-sdk-host-source-sc-2.4.1-dev.1.zip
```

Verify the generated bytes against the audited archive identity, as well as the embedded source, version and member inventory, before configuring. The preset fixes the source commit to the coordinated candidate:

```sh
export SCUBA_DEV_SDK_ARCHIVE_DIR=/path/to/assets
export SCUBA_DEV_SDK_HOST_SHA256=d8118e8898de8daac0cff6f4c9b645cd722a32a5b5924c21c7dae2538074323a
export SCUBA_DEV_CORE_COMMIT=d06f9124d6d7d380295ada4bc2af8968b98a051c
python tools/verify_dev_sdk.py "$SCUBA_DEV_SDK_ARCHIVE_DIR/sco-sdk-host-source-sc-2.4.1-dev.1.zip" "$SCUBA_DEV_SDK_HOST_SHA256" "$SCUBA_DEV_CORE_COMMIT"
cmake --preset coordinated-core-development
cmake --build --preset coordinated-core-development
ctest --preset coordinated-core-development --output-junit full-ctest.xml
```

The preset fixes the full Core source commit and requires the local directory, a full SHA-256, checked lifecycle enabled, and matching lifecycle/archive hashes. Missing or inconsistent inputs fail closed; there is no development release download. Configure rechecks the archive hash, metadata and complete member inventory and tests the checked-lifecycle API. Use a fresh build tree for each coordinated input and rebuild every C++ consumer together: Core's `Platform` and `HostReport` layouts have changed even though the plugin C ABI is frozen. A configuration or a syntax-only check is not a linked build, runtime verification, or evidence of safe operation in a game.

The default plain CMake command still selects the published 2.4.0 stable profile for historical release workflows. The separate `core-main-bf56-rehearsal` preset and its workflow retain their original inputs and evidence; neither is this development candidate. A full-toolchain local rebuild and applicable test suites are still required against the final archive on each supported platform.

The distinct `Coordinated development candidate` workflow packages and verifies the pinned Core host-source archive once, then passes those exact bytes to fresh Linux and Windows/MSVC engine builds and CTest runs. Core commit `d06f9124d6d7d380295ada4bc2af8968b98a051c` must first be reachable in `scuba-sc/sco-core`; until then the packaging job fails. The workflow tests the exact pull-request head (or push/dispatch SHA), not an implicit merge result. A green result would cover only the jobs and tests actually run, not native game activation.

This is a host-source engine lane. It does not consume the separately packaged development plugin SDK or run the standalone plugin-archive consumer. That existing optional consumer is hard-coded to the published 2.4.0 archive and must not be pointed at a development archive as if it covered this candidate. Linux installs Lua 5.4 for the generated-plugin Lua checks. Windows builds its test-only Lua 5.4.8 CLI with MSVC from `https://www.lua.org/ftp/lua-5.4.8.tar.gz`, checking the upstream SHA-256 `4f18ddae154e793e46eeab727c59ef1c0c0c2b744e7b94219710d76f530629ae` before reading source members. This does not replace Core's embedded Lua or change the frozen plugin C ABI.

Both CI platforms enable `SCUBA_REQUIRE_GENERATED_LUA`, verify the interpreter version by executing it, and require the generated-plugin CTest's `--require-lua` argument. Missing interpreters and failed Lua checks fail the lane rather than reporting native-only success. Local/historical profiles keep their optional Lua behavior unless this option is enabled. Windows coverage is established only after the exact-head Windows job executes the generated Lua checker and embedded-builder harness successfully; a prepared workflow or a Linux run is not Windows runtime evidence. Native game startup remains disabled and no game execution is claimed.
